# Hearth security model

This is Hearth's threat model and its **security contract**: what Hearth protects, who from, and what happens
when each of them gets in. Every row of the contract names the automated test in `test/` that checks it. The
suite runs on every push and pull request (`.github/workflows/hearth-security.yml`), together with dependency,
secret and container scans. Run it locally with `npm test`. A few tests need a tool that isn't always installed
(Chromium with Playwright, Electron, a Java compiler, some shell tools); without it they say "skipped" instead of
passing, so check the run's skip count.

Found a problem? Please tell the server owner privately (not in a public channel), with steps to reproduce.

---

## 1. What we protect

| Asset | Where it lives | How it's protected |
|---|---|---|
| **Messages and files** (DMs, server channels, attachments) | Server database and `data/uploads`, as ciphertext only | End-to-end encrypted on the sender's device: AES-256-GCM with a fresh key per message (HKDF-SHA256), the conversation, author and key version bound in. Channel messages and key handoffs are signed (ECDSA P-256). Message text is padded so its length doesn't leak. **File sizes are not hidden:** an encrypted file is its exact size plus 28 bytes. Since 1.29.0 each new message also carries inside its encryption (and signature, in a channel) an id of its own, what it replies to, its thread, when it was sent and its edit count, so readers' apps flag one whose place, time or version the server changed (detection, not prevention: row 139 and §4). |
| **Disappearing messages** | Server database and `data/uploads` until their time, then deleted (backups made before then keep them until those are pruned) | Each conversation's timer (off, 1 hour, 1 day, 1 week or 4 weeks) is stamped on each message when the server stores it. From then on the server hands it out nowhere, the sweep deletes it with its files, reactions, votes, saved entries and pin history, and the apps hide it at its time by themselves. Copies of its words the app keeps in the browser (inbox, reminders) go with it, or the next time Hearth opens if it was closed then; signing out removes them. **The host does the deleting** and anyone can screenshot (§4). |
| **Scheduled messages** | Server database, as ciphertext only, until their time | Encrypted on the sender's device when scheduled, exactly as if sent then (signed too, in a channel), next to the sender's own copy sealed with their vault key. At its time the server posts the ciphertext as a new message; it never gets the text. **The server knows where and when each one will go.** The time it's due is inside it, set only by the sender's app (from their own copy, a time they pick, or Send now; never a time the server gives), so readers' apps flag one posted more than 10 minutes early or more than a day late; within that the server decides when it goes. Every recipient's app can tell a message was scheduled and when it was due (rows 140 and 141, §4). |
| **Passwords** | Never leave the device | Argon2id (64 MiB, 3 passes, per-account salt) in the browser. One half signs in; the server stores only a **bcrypt hash** of it. The other half unlocks your keys and never leaves the device. |
| **Identity keys** (ECDH P-256 + ECDSA P-256) | Private halves on the server, locked | Locked with AES-256-GCM under the password-derived key. The server can't open them. It hands the locked copy out only after the password: at sign-in, with a reset link, or when you re-confirm (password, plus a two-factor code when that's on). A session token alone doesn't get it. |
| **Recovery keys** | Only with the person (password manager or paper) | 160 random bits. They lock a second copy of the identity key; the server stores only that locked copy. |
| **Sessions** | Server database | Only a **SHA-256 hash** of each 256-bit token is stored. Each session ends when revoked, after 60 days unused, or 365 days after sign-in. Ending one also closes its live connection, stops its push notifications and stops its picture-proxy links. A password change, turning on 2FA and "Log out all other devices" with the password give the session a new token in place, which does the same to a copy of the old one (rows 7 and 128). |
| **Two-factor secrets and backup codes** | Server database | The TOTP secret is encrypted with the server's key (`data/secret.key`). Backup codes are HMACs keyed with it. Codes are single-use and attempts are rate-limited. |
| **Email addresses** | Server database | Shown only to the account itself, masked in the admin view. Used only for resets and security notices. |
| **Reset links and email codes** | Server database | Stored hashed, single-use, short-lived (30 minutes). A reset link stops working when the password changes, or when the email address it was sent to changes or is removed. |
| **Group membership, who talks to whom, when** | Server database | **Not hidden** (metadata). The server needs it to route messages. See §4 for the full list. |
| **SMTP password, API keys, payment secrets, alert channels** | Server database or `.env` | In the database, sealed with `data/secret.key`: the SMTP password, the GIPHY, KLIPY, Last.fm and RAWG keys, the Ko-fi token, both Stripe webhook signing secrets, the memberships Stripe key, and alert channels' addresses, ntfy topics, access tokens and webhook signing secrets (shown only masked; row 149). **The call relay (TURN) secret is stored in plain text**, because the relay setup scripts read it. Never in git. |
| **Study tools data** (decks, assignments, timer settings, stats) | Server database, as ciphertext only | Encrypted on your device with a key derived from your identity key (ECDH with itself → HKDF → AES-256-GCM). Each item is bound to its id and kind, so the server can't swap them. For reminders, the server stores only a time. |
| **Server folders, tracked feeds** | Server database | Not encrypted: they're personal settings the server needs (folders) or acts on (it fetches the feeds). They're only shown to the account itself. |
| **Saved messages, read markers, notification settings** | Server database | Message ids, times and settings only. Notes on saved messages are encrypted on your device with a key only you can derive. Drafts, the inbox and reminders stay in your browser: drafts go when you send, all three when you sign out or delete the account, and inbox and reminder copies of a disappearing message at its deadline (any past it are dropped whenever Hearth opens). |
| **Word filters** (for messages) | Server database: your own list as ciphertext only; a server's suggested list in plain text | Your list is sealed on your device with your personal vault key, bound to your account and padded to 8 KB steps: the server never sees a word of it, or which servers' suggested lists you turned off. Matching happens only in each reader's app, which tells the server nothing about matches (rows 142 and 143). **A server's suggested list is visible to every member and is only a suggestion: it can't stop anything being posted** (§4). |
| **Bot tokens and webhook secrets** | Server database | Tokens are stored only as SHA-256 hashes and shown once; webhook signing secrets are sealed with `data/secret.key`. |
| **Server logs** | stdout (journald, Docker logs) | Structured lines with secrets, tokens, message content and ciphertext redacted; IPs truncated unless `LOG_FULL_IP=true`. |
| **Public pictures and songs** (avatars, banners, backgrounds, server icons, emoji, the GIF library, profile songs) | `data/uploads`, readable by anyone with the link | Not encrypted: everyone is meant to see them. The server strips hidden metadata (EXIF and GPS position, XMP, IPTC, comments, data after the image) from JPEG, PNG, WebP and GIF uploads before storing them, GIF comment, plain-text and editors' blocks included, and tags from profile songs (MP3 ID3, APE and Lyrics3 tags; WAV metadata chunks; M4A tags, cover art and purchase details). OGG songs keep their comments, and pictures and songs uploaded before 1.29.0 keep theirs. |
| **Backups** | `data/backups/encrypted/*.hbk`, plus off-site copies | Encrypted with a separate backup key, made tamper-evident in chunks, and restore-tested when made. The plain snapshot a backup is made from only ever sits in the private folder `data/backups/.tmp`, and is deleted afterwards. |
| **The audit log** | Server database, plus `data/audit-anchor.json` | Append-only (the database refuses edits and deletes). Each entry is chained with an HMAC keyed from `data/secret.key`, and the newest entry is recorded in `data/audit-anchor.json`. Anyone without that key can't edit, delete or cut off entries unnoticed. Someone with root (the database and the key) can still rewrite it. |

## 2. Who we protect against

| Adversary | What they have |
|---|---|
| **Random internet attacker** | Can send any request to the server. |
| **Direct visitor** | Reaches Hearth's port without going through the reverse proxy (a LAN, Docker's published port) and can send any header, including a made-up `X-Forwarded-For`. |
| **Database thief** | A copy of `hearth.db`, for example from a stolen disk image or backup. Not the running server's memory. |
| **Stolen-session attacker** | One person's sign-in token (malware, a borrowed laptop, a shoulder-surfed token). A token alone doesn't give the password or the private key. |
| **Compromised email account** | Can read the victim's email, including reset links. |
| **Malicious user** | Has a normal account and tries to read or change others' data, climb permissions, or slow the server down for everyone. |
| **Compromised admin** | A staff account (moderator or admin) turned against the server. |
| **Server compromise** | Root on the VPS, or full control of Hearth's process. This includes a host who decides to spy. |

## 4. What each adversary can still do (honest limits)

- **Server compromise is the big one.** Someone who controls the running server can't decrypt stored messages, but
  could change the web app it sends to browsers so the *next* sign-in leaks a password or keys. This is true of
  every end-to-end encrypted web app. Mitigations:
  - the desktop and Android apps load the same code from the server, so they don't help here;
  - the desktop app adds native powers: a compromised server can offer it updates. Apps built with
    `UPDATE_SIGNING_KEY` refuse unsigned ones, but builds made before signing, forks without the key and the first
    update to a signed build install them after asking. In the desktop app the page can also get the whole screen
    for about 3 seconds after you pick something to share (row 56);
  - **run the server on a machine you trust, keep it updated, and use `scripts/harden-vps.sh`** (firewall,
    SSH keys only, automatic security updates, Hearth as an unprivileged sandboxed user, see §5).
- **A malicious server can also:**
  - add a hidden member to a server, who is then given the key, or hold back a key change after someone leaves,
    or roll the key back across a page reload. Apps refuse keys from non-members and older keys within a session,
    but nothing binds the member list into the key. Compare safety numbers when it matters;
  - add a listener to a call: apps warn about a connection to someone the server never listed and close one to
    someone it doesn't list after 20 s (row 90), but not a listener it lists openly, or lists again for a moment at
    least every 20 s;
  - replay a message, move it under another reply or into or out of a thread, change its time, or serve a version
    from before an edit. Since 1.29.0 apps flag this on new messages (row 139), so it's detected, not prevented, and
    only within limits: messages from older apps, bots, webhooks and the news bot carry nothing to check; a second
    copy is caught only while both are loaded, and a rollback only on a device that saw the newer edit (each keeps up
    to 2,000 edited messages, so a server with very many accounts can wear that down); a time is flagged only when
    it's more than 10 minutes off (a scheduled message: early, or more than a day late), and the sender's app sets it
    with the clock correction the server gives it at start-up, so a server that lies about its clock can shift a
    sender's times by up to a day unflagged; a reply shown without its original reads as "no longer available" if the
    server also denies that original whenever the app asks for it. It can't change a message's content or author
    (except in DMs from early versions of Hearth, marked "Older encryption format", where it can show one as written
    by the other person);
  - read which GIFs people pick (the app reports picks to build the server's GIF library) and, with the GIF proxy
    on, which ones each person loads.
- **Metadata is visible to the server**: who is in which server, who messages whom and when, reactions, server and
  channel names, nicknames, profiles, online status (and when you go Away), game/music activity, file sizes, who
  was @mentioned (for push), GIF picks, when and where (never what) you search, and where and when each scheduled
  message will go.
- **Private channels share the server's key.** Every member holds it; private channels rest only on the server's
  access checks. A bug in those, or a malicious server, opens them to any member.
- **Private category names can be confirmed by guessing.** Categories are names shared by the whole server, not
  objects with permissions of their own. Someone with Manage Channels who types a guessed name into Create channel,
  Edit channel or Rename category is refused when it names a category of channels they can't see, while a made-up
  name is accepted. So they can confirm the name exists, never its place in the order or its channels, and they
  can't put anything into it (row 114). This stays until categories get an identity of their own.
- **Online status and profiles reach everyone on the instance.** Presence goes to every connected user, and any
  signed-in user can look up any profile. Blocking doesn't hide them (invisible mode hides presence).
- **Automatic Away shows when you're using Hearth.** Apps report going idle as it happens, and presence reaches
  everyone signed in on the instance, people you've blocked and people who share no server with you included: the
  switch to Away tells them roughly when you stopped (within about 15 seconds plus your Away time), and the switch
  back the second you return. In the desktop app any input on the computer counts, and the server's page can read
  the computer's idle time (row 117). "Never" (Settings → Privacy & safety), Invisible or Do Not Disturb turns it
  off.
- **Nicknames aren't private.** The server stores them as they are, and every member of that server (and its bots
  with member access) sees them. Every name someone went by stays in the server's audit log for up to a year, also
  after they leave; once their account is deleted the log stops showing the names, but its rows keep them until
  retention removes them. The 10-an-hour cap on your own changes is kept in memory, so a restart resets it. Display
  names don't yet drop invisible characters the way nicknames do.
- **News bot posts aren't end-to-end encrypted.** They come from public feeds and the server writes them.
- **Without 2FA, an email compromise takes over the account** (row 10), so turn on 2FA. Its new keys get no server
  or group key until a member who knew the person verifies them there, or an instance admin does (rows 136 and
  137), but:
  - direct messages and calls aren't held back: a device that never saw the old key trusts the new one on first
    use, as for any contact, and writes new DMs to it, and the account can still join calls;
  - a member who is fooled into vouching opens the servers and groups they're in themselves; invite links made
    before the reset keep working; once the mark has gone, servers joined afterwards aren't held;
  - accounts reset before 1.29.0 weren't marked, so they're trusted as before (devices that had pinned the old key
    say "Security key changed"; others trust the new one on first sight);
  - if every server or group an instance admin was in before their reset holds a second account of the
    attacker's, those accounts can clear the admin's mark, and the admin can then verify other taken-over accounts
    from Admin → Users.
- **A short two-factor grace for two low-risk changes.** Starting a data export and an admin's clean-up of unused
  files accept a two-factor pass on this session from the last 10 minutes; every other re-confirm asks for a fresh
  code (row 6).
- **A copied sign-in token works until the token is replaced** (row 128). Until then it can do what the session
  can, short of the changes that need the password: it can sign out the account's other devices (it gets no new
  token) or log the session out, which ends it for the original device too. If the copy was in a call when the
  token was replaced, its place there is kept, shown as reconnecting, for the reconnect grace (18 s by default,
  `VOICE_GRACE_MS`), and media already flowing between it and the others may go on until then; it can't resume the call.
- **Old-format accounts are recognisable.** Accounts still on the old (PBKDF2) password format can be told apart
  from unknown usernames through `/api/auth/params` until they sign in once.
- **The robot check is proof of work.** Graphics cards and native code solve it much faster than browsers, so it
  raises the cost of a flood without capping it. Someone who keeps solving it can hold up a brand-new device on a
  new network from signing in for a while (10 tries per 15 minutes, 100 a day).
- **A compromised admin** can suspend users, remove someone's 2FA (only for people ranked below them; it's logged
  and the person is emailed), read the audit log and see IP addresses. With their password (and a fresh two-factor
  code when it's on) they can also mark an account that was reset without its recovery key as verified, so
  members' apps share every server's and group's key with it (logged; row 137). They can't read messages, act on
  the owner, or erase the log.
- **No forward secrecy for history.** Your long-term key can decrypt your past messages, so they follow you to new
  devices. Someone with your password **and** a copy of the database could read your history. Changing your
  password re-wraps the same identity key; it doesn't replace it. The database copies made before upgrades
  (`data/backups/hearth-before-v*.db`) aren't encrypted; only the newest `PRE_UPGRADE_KEEP` (3 by default) are kept
  after each upgrade that goes through (row 135).
- **Attachment rules are best effort.** The real attachment list is inside the encrypted message, so the server
  can't enforce "Attach files" or clean up files that were never declared. Uploaded files are served to anyone
  who has the link.
- **Other sites see people's IP addresses** for: an image link in a message once the reader clicks Load image (or
  straight away for someone who chose Always load), a watch-together video file from another site once the viewer
  clicks Load video, the YouTube, Vimeo and Twitch players, and the default STUN servers (Google). With the GIF
  proxy off, GIPHY and KLIPY GIFs are outside pictures like any other. The app's fonts, GIFs (with the GIF proxy
  on), news pictures, webhook avatars and game and music art go through the server, so those sites don't see
  readers (row 130).
- **The security policy still lets pictures and media load from any https site** (row 25): that's how an image link
  loads once it's opened, and a watch-together video file. So injected markup could still send data out in a
  picture or media address. Closing that needs every outside picture and video to go through the server, which
  would then fetch (and see) every link people open.
- **The picture proxies still fetch what others chose** (row 132). Whoever writes a feed chooses its pictures, so
  someone who follows a feed they host can have the news proxy fetch public pictures of their choosing, a few items
  at a time. GIF proxy links aren't signed, since the server can't read the messages they're in; that proxy only
  reaches GIPHY's and KLIPY's media hosts. A webhook avatar on any host but Discord's, GitHub's and Gravatar's
  shows the webhook's own picture until an admin lists that host in `WEBHOOK_AVATAR_HOSTS`, which then lets the
  avatar proxy fetch from it, on the local network too.
- **Calls survive short blips, not long outages.** After a dropped connection or a server restart the app rejoins
  the call by itself within the grace window (18 s by default, `VOICE_GRACE_MS`; row 89); past that, the call ends.
- **The relay:** relay logins can't be revoked early, anyone who can sign up can get one, and the relay secret is
  shared by every region and stored in plain text. The hand-written `deploy/turnserver.conf` has no bandwidth cap
  (`setup-turn.sh` adds one; installs from before need it run again).
- **Push:** anyone can make the server send an opaque, encrypted push to any public https host with a real
  certificate (that's how web push works). They get no answer back. The server's own public addresses stay
  reachable on ports 80 and 443; behind NAT, list the public IP in `OUTBOUND_BLOCK`.
- **Server update zips are signed, but the first key is trusted on first use.** Until a server has pinned an update
  signing key (row 60), only the checksum protects an update, so a swapped zip with a matching `.sha256` would be
  installed. Servers with neither OpenSSL 3.0+ nor Node can't check Ed25519 and stay on the checksum. Root on the
  server can change the pinned key. Compare the pinned key (`hearth-update --status`) with the one in the release
  notes.
- **Disappearing messages are deleted by the host.** A malicious or compromised server can skip deleting, keep
  copies of the ciphertext or stop the sweep, and anyone whose keys later leak could read those copies (there is no
  forward secrecy). The server also controls each message's send time, so it can make one look newer and keep it on
  screen longer (on messages from 1.29.0 apps, by up to 10 minutes before apps flag it: row 139). Anyone can
  screenshot, copy, forward, download, export or report what they see. The server knows each conversation's timer,
  who changed it and when each message is due to go.
- **Scheduled messages wait on the server.** Until its time, the server holds the ciphertext and knows that a
  message is coming, where (conversation and thread), when, its size, and which session wrote or last edited it.
  It is trusted to post it on time and only once: the time it's due and its own id are inside it, so readers' apps
  flag one posted more than 10 minutes early or more than a day late, or a second copy while both are loaded (row
  139), but within that day it decides when it goes. Every recipient's app can tell a message was scheduled and when
  it was due. It is also trusted to really delete a cancelled one: a dishonest server, or a restore from an older
  backup, can bring a cancelled message back into the same conversation. A stolen session can't get the sender's app
  to bring one back by itself (row 121), but it can put an earlier copy of a scheduled message that is still waiting
  in place of the current one (the words from before an edit: a copy names its scheduled message, not which
  version), and the sender's app re-encrypts and signs that copy by itself after a key change. And, as with any
  message while the key is unchanged, a stolen session can post the sender's signed ciphertext again (readers' apps
  flag the second copy while both are loaded, row 139). Holding a signed-out session's messages is the server's
  doing too, so it stops a stolen token, not the server, and `restore --sign-out-everyone` doesn't hold what the
  signed-out sessions scheduled.
- **The word filter for messages only changes what each reader sees.** It can't stop anything from being posted,
  and people can spell around any list: digits or symbols for letters, a letter written exactly twice, a Cyrillic
  word spelled in Latin letters in an all-Latin message. A word over 256 characters is compared only by its ends, and
  text past a message's first 50,000 characters isn't checked. Each member can turn a server's suggested list off,
  and that list is plain text every member and the server can read. Only a device that has opened a newer copy of
  your own list notices the server handing back an older one or none, so a device signing in for the first time
  takes what it's given (rows 142–145).
- **Hiding history from new members is the server's doing** (row 146), like private channels: it decides when keys
  change and who is listed as missing one, so a malicious server can skip the new key, or have members' apps share
  the current one with a newcomer. Off (the default), a new member reads the current key's backlog. Deletions still
  go to everyone who can see the channel, so a newcomer's app gets the ids (and thread ids) of messages from before
  they joined as those are deleted, though nothing it can open. Group chats don't have the setting.
- **Android notifications (closed app) depend on a push app.** With ntfy (self-hosted or ntfy.sh) or a
  distributor that uses Google's service, that service sees when a push arrives for the device, not what it says.
  Native parts of the Android app are only build-checked in CI until they're tested on a real phone.
- **Link previews show the server the links you preview.** When someone presses Preview (or uses Always mode), the
  server fetches the page for them, so it learns those links, who asked and when, and the size of the encrypted
  message sent just after can tie the link to a conversation. In Always mode that includes links typed and deleted
  before sending. The site sees the server's address, and fetching can use up a one-time link. A modified app can
  send a card that says anything except its domain line, which readers work out from the link.
- **`trustedSelfSignedHosts`** in the desktop app accepts any certificate for those hosts. Leave it empty so the
  app asks once and pins that exact certificate.
- **The audit log** can be rewritten by root. Someone who can write the data folder but lacks the key can make it
  look like a log from before the keyed chain; Hearth then starts a new signed section and shows the date, so the
  reset shows, but edits before it can't be proven.
- **Supporter payments** ignore refunds and chargebacks; unmark the supporter by hand in Admin → Users.
- **Session location** ("Reno, NV") isn't shown, only the IP address: showing a place needs a GeoIP database or
  sending everyone's IPs to a third-party service.
- **Rate limits and the security log are kept in memory**, so a restart resets them, and a multi-server setup
  would need a shared store. The in-memory security log keeps the last 500 failed sign-ins, robot-check failures
  and blocked addresses. Every request is also written to the structured server log (access log: route, status,
  a keyed user pseudonym, a truncated address; docs/OPERATIONS.md), and staff actions and account security events
  go to the audit log.

- **Bot messages and slash-command text aren't end-to-end encrypted.** What you type after a bot's command goes to
  that bot's operator (the app warns first), and the bot's posts are readable by the server.
- **Reading habits are metadata.** The server knows how far you've read in each conversation, which message ids you
  saved, your mute choices and quiet hours, and who was mentioned, but not what any message says.
- **Uploaded files are served without sign-in, by design.** Blob names are random and the contents are ciphertext
  whose key is only inside the message. Profile pictures and server images are not encrypted.
- **Calls:** ICE candidates are not signed, so a malicious server can reroute or disrupt a call (not decrypt it).
  The server decides who is in a call; an extra participant it lists openly is not detected. Media is DTLS-SRTP
  between participants, with no extra media end-to-end layer yet (see `docs/VOICE.md` for the staged design).
  Handshakes are checked against signing keys pinned on first use (row 152), so on a first call between devices that
  haven't pinned each other the server could sit in the middle (safety numbers catch it). Old signed offers can be
  replayed to break a connection, though not to listen in. RTP headers aren't encrypted: a relay or anyone on the
  path sees a loudness level on every audio packet and which stream is camera or screen, besides sizes, timing and
  addresses. The server sees who is in each call, every handshake and every ICE candidate (participants' local and
  public IP addresses), and in a call without a region, participants get each other's local and public addresses
  too, so anyone allowed to join (Connect, which `@everyone` has by default) can collect them; a call pinned to a
  region goes through its relay only.
- **A plain restore brings back sessions** that were signed out after the backup was made. After a break-in, restore
  with `--sign-out-everyone`.
- **Monitoring is per process.** Job health, alert counters and the security log live in one server; Hearth can't
  report that it is down itself, so point an external monitor at `/api/health/ready`.
- **Alert channels and `/metrics`.** An alert that doesn't get through to a channel isn't sent again (the next alert
  or a Test tries). A webhook channel keeps its signing secret when its address changes, so the new receiver could
  replay a signed alert to the old one within that receiver's time window; remove the channel and add it again for a
  new secret. On a public ntfy server the topic is the password for reading it, so pick one nobody can guess. Wrong
  `/metrics` tokens lock the network they came from out for up to 10 minutes, the right token included (row 151), so
  someone sharing the scraper's network can keep it from scraping; scrape from an address of your own
  (docs/OPERATIONS.md).

## 5. Running it safely (infrastructure)

```
Internet ─► VPS firewall (ufw: 22, 80, 443, relay ports) ─► Caddy (HTTPS, HSTS) ─► Hearth (uid 1000, sandboxed)
                                                                              └─► data/ (SQLite file — no network database)
```

- **Docker** (`docker-compose.yml`, and `deploy/compose.image.yml` with the published image):
  - Hearth runs as uid 1000 on a read-only filesystem, with no Linux capabilities and no-new-privileges, a
    process limit and rotated logs.
  - No Docker socket is mounted.
  - Caddy reaches Hearth over an internal network. With a domain, set `HEARTH_BIND=127.0.0.1` so port 3000 isn't
    public: Docker ports bypass ufw.
  - `TRUST_PROXY` defaults to the compose file's own Caddy network. A value in `.env` replaces it; never set it to
    a number or to Docker's gateway (`x.x.x.1`) unless `HEARTH_BIND=127.0.0.1`.
- **systemd** (`deploy/hearth.service`):
  - A dedicated `hearth` user; the whole system is read-only except the data folder (`ProtectSystem=strict`).
  - No capabilities, a system-call filter, and private `/tmp`; home folders are hidden.
  - Program files are owned by root, so Hearth can't change its own code.
- **The VPS** (`scripts/harden-vps.sh`):
  - Firewall on; SSH password logins off, but only once a key works, so you can't be locked out.
  - fail2ban, automatic security updates.
  - Moves a root-run Hearth to the sandboxed user, rolling back if it doesn't come up.
- **Client addresses**: behind a proxy on another machine or container, set `TRUST_PROXY` to its address, or every
  visitor shares the proxy's address (and one set of sign-in limits). Hearth's log names an ignored proxy once.
- **Database**: SQLite, a file inside `data/`. It never listens on a network port, so there's nothing to expose.
- **Secrets** (`.env`, `data/secret.key`, `data/backup.key`, SMTP password, API keys):
  - never committed: `.gitignore` covers them and `gitleaks` scans every push;
  - turn on GitHub secret scanning and push protection too.
- **Desktop releases**: set the `UPDATE_SIGNING_KEY` secret and `UPDATE_PUBLIC_KEY` variable (see `docs/SIGNING.md`;
  if you already have the secret, set the variable to its public half rather than making a new pair)
  and `VPS_HOST_FINGERPRINT` with the server-copy secrets, the secrets in the `production` environment with its
  protection rules (only the default branch and `app-v*` tags; required reviewers if you want them), then delete
  the repository secrets of the same names, or any branch's workflow can still read them. Use a deploy user that
  can only write `data/downloads`, not root.
- **Android releases**: your own signing key in the `ANDROID_KEYSTORE_*` secrets. CI never makes or keeps one;
  without it the APK is built unsigned and never published. If earlier builds used the key older workflows kept in
  the Actions cache, it's exposed: delete the `hearth-android-key-v1` cache entry and the old branches that still
  carry that workflow, remove APKs signed with it from `data/downloads` and old releases, update
  `ANDROID_CERT_SHA256`, and have people uninstall and reinstall once (`mobile/README.md`, "Moving off the old
  built-in key").

## 6. Backups

- **Encrypted full backup every day**: database, keys and uploads in one `.hbk` file. It's encrypted with
  `data/backup.key` (or `BACKUP_KEY`) using AES-256-GCM in chunks, so any change, reordering or truncation is
  detected.
- **Restore-tested automatically**: each backup is decrypted into a scratch folder and the database is
  integrity-checked right after it's made. Admin → Owner shows the result, and "Test restore" repeats it.
- **The plain snapshot** a backup is made from lives only in `data/backups/.tmp` (readable by Hearth alone). It's
  deleted when the backup is done, at shutdown, and at start-up if a crash left one.
- **Off-site**: set `BACKUP_RCLONE_REMOTE` and each backup is copied with rclone (Backblaze B2, S3, Google Drive,
  SFTP…). With Docker, run rclone on the host over `data/backups/encrypted/` instead, ideally with
  `--include '*.hbk'`.
- **Disappearing messages** are in every backup made before their time until that backup is pruned (daily
  encrypted backups, region copies, `hearth-auto-*.db`, and `hearth-before-v*.db` once it's no longer among the
  newest `PRE_UPGRADE_KEEP`); off-site rclone copies and update snapshots keep them until deleted by hand. A restore deletes those already past their time at the first start,
  before anyone can connect.
- **Keep the backup key somewhere else** (Admin → Owner → "Show backup key", which needs your password and is
  logged). Never store it next to the backups.
- **Restore on a new machine**: `node server/cli.js restore <file.hbk> <empty-folder> <backup-key>`, then start
  Hearth with `DATA_DIR` pointing there. `restore` only writes into an empty folder and refuses a backup from a newer
  Hearth (exit 2). While it runs the folder holds `RESTORE-INCOMPLETE`, and Hearth won't start on a folder that has it.
  Add `--sign-out-everyone` after a break-in.
- **Missing files are reported, not hidden**: a backup made while files the database refers to are missing still
  completes and lists them (CLI exit 3, audit entry `backup_files_missing`); `node server/cli.js check-files` gives the
  same report for any data folder. A failed backup (disk full, for example) leaves nothing behind and is audit-logged.
- **Drills**: `node scripts/recovery-drill.js` and `bash scripts/upgrade-drill.sh` prove recovery and upgrades end to
  end; see `docs/RECOVERY.md`.
- **Plain database copies** (`data/backups/*.db`, for undoing updates) never leave the server and can't be
  downloaded. The ones made before upgrades (`hearth-before-v*.db`) are pruned after each upgrade that goes
  through, keeping the newest `PRE_UPGRADE_KEEP` (3 by default; row 135).

## 7. Supply chain

- **Lockfiles**: `npm ci` in CI (server, desktop and Android), in the Docker image and when the updater builds a
  new version. The updater's rollback falls back to `npm install` only when the old libraries weren't saved.
- **Dependabot** (`.github/dependabot.yml`): weekly for npm (server, desktop, mobile), GitHub Actions and Docker
  images.
- **CI** (`hearth-security.yml`) runs on every push, every pull request and weekly:
  - the security test suite;
  - `npm audit` (fails on high or critical in server dependencies);
  - gitleaks over the full git history;
  - a Trivy scan of the Docker image (fails on fixable high or critical) and of its configuration;
  - CodeQL (`security-extended`; `.github/codeql/codeql-config.yml` says what's left out and why).
- **Release workflow** (`hearth-apps.yml`): read-only token for every job except the one that creates the GitHub
  release; Android installs exactly what its `package-lock.json` lists; installers reach people's apps only from `app-v*` tags and the default branch; the server copy needs a
  pinned host key; the jobs that sign update files or publish run in the `production` environment, install no npm
  packages, and publish only the final artifacts (never an unsigned APK, the Play bundle or SignPath's inputs).
- **Server updates**: zips are signed with the publisher's Ed25519 key (`scripts/update-key.js`, run by
  `make-update-zip.sh`); the key stays on the publisher's computer and servers pin its public half in
  `/etc/hearth-update.pub` (docs/SIGNING.md, "Signing server updates").
- **Image workflow** (`hearth-image.yml`): the Docker image is built and published only from `hearth-v*` tags that
  match `package.json`, in the `production` environment, with a read-only token for everything but the package push.
  Trivy scans it before the push, in a job of its own with a read-only token, so the scanner never runs next to the
  token that can publish; the image carries a build provenance attestation and an SBOM (row 153). Add `hearth-v*` to
  the `production` environment's allowed tags.
- **Actions pinned**: every action in every workflow is pinned to a full commit SHA.
- **On GitHub** (Settings → Code security), switch on: Dependabot alerts and security updates, secret scanning,
  and push protection.
